## 1. Most important finding

The deepest divergence is:

```text
EXISTING_PM1 = VENUE_SITE_FIRST__HIVE_COMMUNITY_OPTIONAL
ASTRA = SPECIALIZED_HIVE_FRONTEND__HIVE_FOUNDATIONAL
```

This matters more than visual differences.

Existing PM1 intentionally allows a complete public venue presence with no Hive activation. This broadens the addressable website-builder product and reduces onboarding dependency, but it weakens the answer to the founding question “why build this on Hive at all?”.

Astra keeps the business/venue experience primary at the user-interface layer while keeping Hive primary at the architecture/social-identity layer.

Under the founding HiVenues experiment, Astra's interpretation is stronger.

This does **not** imply that visitors should be forced to sign in, see blockchain jargon or use a Community page. The comparison independently supports public browsing before sign-in and venue-native language.

## 3. Where Astra materially improves the product hypothesis

Astra contributes four high-value ideas beyond visual novelty:

1. **Hive foundational, venue-native in presentation.** Hive disappears as jargon without disappearing from the architecture.
2. **Events as durable social contexts.** A real-world event and its Hive discussion identity remain linked across edits, and patron stories can retain event identity.
3. **Human-action vocabulary.** Share a moment, Join the room, Support and related language translate protocol primitives without hiding consequences.
4. **Commercial-product Studio shell.** The same semantic architecture is presented with stronger hierarchy, clearer task modes and a more polished venue canvas.

These are synthesis candidates, not authorization to copy code/assets.

## 4. Where existing HiVenues materially outperforms Astra

Existing contributes capabilities that must not be thrown away during convergence:

1. **Deep semantic/domain model.** Multiple pages, navigation, resources, media, events, programs, menus, equipment and capability bindings are modeled explicitly with stable ids.
2. **Authoring transaction integrity.** Proposal/apply/discard, expected digests, stale-input rejection, exact inverse history, shared-resource consequences and explicit durable checkpointing are stronger than Astra's local state model.
3. **Security/authority maturity.** Keychain self-signing, Posting/Active separation, server-key minimization, fail-closed capability activation and production provenance are substantially more mature.
4. **Testing/reproducibility.** Cross-platform deterministic gates plus pinned Chromium/browser evidence far exceed Astra's bounded 19-test suite.
5. **Production evidence.** Fourth Street is a real deployed system with health/readiness, rollback and real Hive behavior; Astra is correctly only a local demo.

## 6. Hive architecture adjudication

The comparison rejects two simplistic conclusions.

### Rejected conclusion A

> “Astra is more Hive-native, therefore replace existing Hive implementation.”

No. Existing has the much stronger real integration/security/production layer.

### Rejected conclusion B

> “Existing has real Hive integration, therefore its optional-Hive v2 product thesis is proven superior.”

No. Production maturity does not adjudicate whether Hive should remain structurally optional in the next-generation product.

### Accepted synthesis direction

A later design operation should explore:

```text

+

+

+
PROGRESSIVE_DISCLOSURE_OF_HIVE_MACHINERY
+
EXISTING_KEYCHAIN_AND_AUTHORITY_SAFETY
```

## 7. Issue #199 interaction

Astra should not be used as an excuse to bypass existing typed-authoring work.

Canonical existing HiVenues still has real PM4 gaps, including ticket/reservation action editing, timestamps, general media, component recipe editing and complete fresh-archetype journeys.

Astra demonstrates that a coherent operator product should make such tasks straightforward. The existing project should finish them inside its stable semantic authority model rather than import Astra's flatter schema.

## 9. Highest-information successor

The next operation should be external rather than another internal comparison.

Run a blind, counterbalanced user test with venue operators and patrons.

The goal is to test the synthesis questions exposed by this audit:

- Which Studio mental model lets operators complete real work with fewer errors?
- Does Astra-style venue-native language improve comprehension of Hive actions?
- Does event-social coupling make sense to ordinary patrons/operators?
- Does the stronger Astra visual direction materially improve trust/desire to use the venue?
- Can users distinguish configuration, release/deploy, public Hive posting and financial signing?
- Which existing integrity concepts need progressive disclosure rather than removal?

The convergence ledger defines the task set and measurement categories.

## Claim ceiling

This audit establishes comparative product/architecture evidence only.

It does not establish that:

- Astra is a production replacement;
- existing HiVenues is inferior overall;
- a specific synthesis will succeed with real users;
- Hive must technically be present in every page request;
- any code should be ported before separate authorization.

Truth over attachment to either implementation.
